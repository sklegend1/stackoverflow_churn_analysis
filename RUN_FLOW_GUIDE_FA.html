۱. هدف و دامنه

از صفر تا LSTM

این راهنما مسیر کامل را توضیح می‌دهد: از داده خام تا ساخت مدل LSTM برای پیش‌بینی ریزش، همراه با مرحله‌های میانی که هم برای تفسیرپذیری لازم‌اند و هم برای یادگیری بهتر LSTM.

چیزی که باید از ابتدا روشن باشد: این پروژه فقط یک مدل نیست. یک pipeline است:

داده خام ← event log ← ویژگی‌ها ← feature importance ← core actions ← پنجره زمانی Tp ← برچسب ریزش ← WA/Ap ← ارزیابی زمانی ← LSTM.

این سند برای چه کسی است؟

برای یک کاربر نیمه‌فنی که می‌خواهد بداند هر مرحله چه می‌کند و چگونه باید همان مسیر را روی دیتاست دیگری دوباره اجرا کند.

خروجی نهایی چیست؟

یک مدل ترتیبی LSTM که از توالی رفتار، فاصله زمانی، و زمینه‌ی سگمنت/زمان برای پیش‌بینی churn، Ap و Tp استفاده می‌کند.

۲. مبنای علمی روش

چرا این pipeline معتبر است؟

مبنای علمی این کار از یک مشاهده ساده شروع می‌شود: در بسیاری از محصولات، ریزش یک event رسمی ندارد. کاربر ناگهان حذف نمی‌شود؛ بلکه الگوی فعالیتش کم‌کم تغییر می‌کند. پس باید ریزش را از رفتار استنباط کرد، نه از یک برچسب قراردادی.

اصل علمی معنا در این پروژه اثر روی طراحی
Churn رفتاری است عدم فعالیت آینده بعد از یک grace period، معیار ریزش می‌شود. به‌جای label قراردادی، یک تعریف عملیاتی می‌سازیم.
رفتار کاربران ناهمگن است کاربر فعال، کم‌فعال، متخصص، پرسشگر و ... آستانه‌ی یکسان ندارند. همه چیز per-segment انجام می‌شود.
زمان اهمیت دارد فاصله‌ی بین رویدادها و تغییر رژیم زمانی، بخشی از سیگنال است. Tp، WA و در نهایت LSTM زمان‌محور می‌شوند.
Drift واقعی است معنای فعالیت در سال‌های مختلف یکسان نیست. ارزیابی sliding cutoff و در نهایت مدل sequence-aware لازم می‌شود.
تفسیرپذیری باید بماند مدل ساده‌تر، teacher و explanation layer برای مدل پیشرفته‌تر می‌شود. rule-based + LSTM را با هم نگه می‌داریم.
نتیجه‌ی عملی: اگر فقط یک مدل black-box بسازید، بخشی از فهم سیستم را از دست می‌دهید. این پروژه عمداً از یک مدل تفسیرپذیر شروع می‌کند تا هم baseline داشته باشد و هم مبنای آموزش مدل ترتیبی.

۳. قرارداد داده

چه چیزی لازم دارید؟

قبل از شروع، باید مطمئن شوید که داده شما با این روش سازگار است. اگر این قرارداد برقرار نباشد، نتیجه قابل تکرار نخواهد بود.

نیاز توضیح اگر نباشد
event-level data هر رویداد باید user_id، timestamp و action_type داشته باشد. دیگر نمی‌توان gap، Tp و sequence ساخت.
حداقل چند سال تاریخچه برای دیدن drift و ارزیابی چند cutoff لازم است. نتیجه فقط برای یک دوره خاص اعتبار دارد.
سگمنت‌های پایدار همه آستانه‌ها و teacher targets برای هر سگمنت جدا هستند. مدل از پایه مبهم می‌شود.
برای دیتاست جدید چه کنید؟ اگر سگمنت‌های موجود ندارید، اول یک سگمنت‌بندی روشن و قابل نسخه‌بندی تعریف کنید. اگر سگمنت‌ها را از خوشه‌بندی می‌سازید، artifact، feature list و نسخه‌ی داده را ذخیره کنید تا کاربر جدید هم قابل نسبت‌دادن باشد.

۴. از داده خام تا Event Log

مرحله‌ی پایه‌ای

در پروژه اصلی، داده خام Stack Overflow از چند منبع می‌آمد و بعد به event log تبدیل می‌شد. برای دیتاست جدید هم باید همین منطق حفظ شود: داده خام را به یک جدول رویداد استاندارد تبدیل کنید، نه یک جدول تجمیعی.

مرحله ۴.۱: منبع خام XML / استخراج خام / هر ساختار مشابهی که رویدادها را نگه می‌دارد.
مرحله ۴.۲: لایه‌ی میانی اگر لازم است ابتدا به storage تحلیلی مثل MySQL یا DuckDB منتقل کنید.
مرحله ۴.۳: خروجی شاردشده فایل‌های Parquet یا shardهای مشابه برای پردازش مقیاس‌پذیر.
مرحله ۴.۴: eventlog نهایی جدول رویداد استاندارد با شناسه کاربر، زمان، action type و gap.
فایل / مرحله ورودی خروجی منطق علمی
create_eventlog_v2.py شاردهای خام/processed eventlog_v2.parquet یکسان‌سازی رویدادها و محاسبه gap per user
قاعده‌ی gap: اول داده را بر اساس user_id و timestamp مرتب کنید، سپس فاصله بین دو رویداد متوالی همان کاربر را حساب کنید. 
df = df.sort(["user_id", "timestamp"])
df = df.with_columns(
    (pl.col("timestamp").diff().over("user_id") / 1_000_000)
    .alias("gap_time_actions_seconds")
)
نکته‌ی مهم اجرایی: اسکریپت‌ها باید از دایرکتوری خودشان اجرا شوند. اگر از ریشه‌ی پروژه اجرا شوند، pathهای نسبی و sys.path ممکن است خراب شوند.

۵. Feature Matrix

پایه‌ی سگمنت‌سازی و core actions

در این مرحله، event log به ماتریس ویژگی در سطح کاربر تبدیل می‌شود. این ماتریس برای تشخیص ساختار رفتاری کاربران و استخراج اهمیت اکشن‌ها استفاده می‌شود.

اسکریپت ورودی خروجی چرا مهم است؟
src/data_engineering/create_feature_matrix.py data/processed/eventlog_v2.parquet data/processed/feature_matrix_v2.parquet ورودی مدل‌های تشخیص سگمنت و feature importance
قاعده‌ی فنی: در ETL مقیاس‌دار از Polars lazy scan و collect(engine="streaming") استفاده کنید و pandas را فقط در مرز sklearn / XGBoost به کار ببرید.

۷. Core Event Log و Split

نقطه‌ی اتصال rule-based و LSTM

core event log فقط رویدادهای مهم را نگه می‌دارد. این مرحله هم برای مدل تفسیرپذیر لازم است و هم برای LSTM، چون sequence باید روی فعالیت‌های معنادار ساخته شود نه روی نویز کل رویدادها.

اسکریپت وظیفه خروجی
src/data_engineering/create_core_eventlog_splited.py فیلتر core actions بر اساس core_activity_per_persona_named.csv و split کاربرمحور 80/20 core_eventlog_train_v1.parquet و core_eventlog_eval_v1.parquet

این پروژه نشان داد که نسخه‌ی split شده برای پایپ‌لاین واقعی لازم است. نسخه‌ی غیر split فقط یک core log واحد می‌سازد و برای training/evaluation جداگانه کافی نیست.

چرا split کاربرمحور؟ چون اگر کاربر بین train و eval شکسته شود، leakage رخ می‌دهد و ارزیابی واقعی نخواهد بود. 
# خروجی‌های مورد انتظار
core_eventlog_train_v1.parquet
core_eventlog_eval_v1.parquet
اشتباه رایج: با split event-level یا time-level ساده، ممکن است اطلاعات آینده به training نشت کند. این pipeline عمداً split را در سطح user انجام می‌دهد.

۸. مدل تفسیرپذیر و نقش teacher

Scientific bridge

قبل از LSTM، یک لایه‌ی تفسیرپذیر می‌سازیم که Ap و Tp را به‌صورت داده‌محور استخراج کند. این لایه فقط برای توضیح نیست؛ بعداً نقش teacher برای مدل عمیق‌تر را هم بازی می‌کند.

مرحله اسکریپت خروجی نقش علمی
core actions importance feature importance by XGBoost core_activity_per_persona_named.csv استخراج gain برای هر سگمنت و action
rule-based / temporal search tp_ap_xgboost_enhanced.py tp_ap_xgb_enhanced_best_params_WA_recency.csv تعیین Ap/Tp و ساخت teacher targets
چرا این کار علمی است؟ چون LSTM را از صفر و بدون راهنما آموزش نمی‌دهیم. مدل تفسیرپذیر، یک prior رفتاری می‌دهد و باعث می‌شود خروجی مدل عمیق‌تر با منطق کسب‌وکار هم‌راستا بماند.

۹. آموزش LSTM

مرحله‌ی آخر

LSTM توالی رویدادها را می‌بیند و با استفاده از gain، فاصله زمانی بین رویدادها، ویژگی‌های زمانی و embedding سگمنت، سه خروجی را پیش‌بینی می‌کند: churn، Ap و Tp.

ورودی شکل معنا
sequence [batch, 50, 2] gain و time_delta برای ۵۰ رویداد اخیر
global_feat [batch, 4] days_since_last، era، month، year
persona_feat [batch, 10] → embedding 32 نمایش فشرده‌ی سگمنت از statistics
تابع هدف: 2.0 * BCE(churn) + 1.0 * MSE(Ap) + 0.1 * MSE(Tp)

چرا multi-task؟

چون مدل فقط churn را یاد نمی‌گیرد؛ بلکه Ap و Tp را هم هم‌زمان می‌بیند. این کار regularization ایجاد می‌کند و تفسیرپذیری را حفظ می‌کند.

چرا time_delta مهم است؟

چون drift و شدت فعالیت در فاصله‌های زمانی معنا پیدا می‌کنند. بدون time_delta، LSTM فقط یک نسخه پیچیده‌تر از feature تجمیعی خواهد بود. 

SEQUENCE_LENGTH = 50
PERSONA_EMBED_DIM = 32
LSTM_HIDDEN = 128
NUM_LSTM_LAYERS = 2
BATCH_SIZE = 256
LEARNING_RATE = 0.001
GRACE_DAYS = 90
فایل/آرتیفکت نقش
checkpoints/best_temporal_lstm_model.pt وزن‌های آموزش‌دیده‌ی مدل
checkpoints/lstm_model_metadata.pkl متادیتا، embedding matrix و تنظیمات لازم برای evaluation
نکته‌ی عملی: مدل evaluation هم وزن‌ها و هم metadata را لازم دارد. اگر یکی از این دو را حذف کنید، ارزیابی کامل ممکن نیست.

۱۰. ارزیابی و کنترل کیفیت

چگونه بفهمیم درست کار کرده؟

ارزیابی درست فقط یک عدد F1 نیست. این پروژه نشان داد که باید drift، نرخ پیش‌بینی، و عملکرد سال‌به‌سال را هم بررسی کرد.

نوع ارزیابی چرا لازم است؟ خروجی مورد انتظار
Multi-year evaluation برای دیدن روند drift در سال‌های مختلف csv گزارش yearly results
Per-segment check برای تشخیص سگمنت‌های ضعیف میانگین و std در هر سگمنت
rate_ratio برای فهم over-prediction نسبت churn پیش‌بینی‌شده به واقعی
معیار موفقیت علمی در این پروژه: مدل LSTM باید نسبت به rule-based baseline بهتر شود و هم‌زمان حساسیتش به سال‌های قدیمی کمتر شود. اگر F1 بالا برود اما rate_ratio خراب شود، نتیجه هنوز قابل اتکا نیست.

۱۱. چگونه روی دیتاست جدید تکرار کنیم

روش بازتولید

اگر بخواهید همین روش را روی داده‌ی جدید اجرا کنید، ترتیب مراحل را تغییر ندهید. هر مرحله به مرحله قبل وابسته است.

۱) داده خام را آماده کنید مطمئن شوید هر رویداد actor مشخص و timestamp معتبر دارد.
۲) event log بسازید رویدادها را یکسان کنید و gap را حساب کنید.
۳) feature matrix بسازید تا بتوانید سگمنت‌ها و importance را استخراج کنید.
۴) core actions را انتخاب کنید و core event log بسازید.
۵) split را کاربرمحور انجام دهید تا leakage رخ ندهد.
۶) model تفسیرپذیر را آموزش دهید تا Ap/Tp و baseline داشته باشید.
۷) LSTM را آموزش دهید تا sequence learning و drift-awareness اضافه شود.
۸) ارزیابی سال‌به‌سال انجام دهید و همیشه drift و rate_ratio را گزارش کنید.
قانون طلایی: اگر در یک دیتاست جدید مرحله‌ی ۴ یا ۵ را تغییر دهید، این فقط یک re-run نیست؛ یک آزمایش متفاوت است. پس تغییرها را مستند کنید.

۱۲. چک‌لیست اجرایی

برای دنبال‌کردن گام‌ها
  1. مطمئن شوید داده خام event-level است.
  2. برچسب سگمنت‌ها را مشخص و قابل نسخه‌بندی کنید.
  3. event log را بسازید و gapها را محاسبه کنید.
  4. feature matrix را تولید کنید.
  5. core actions را پیدا کنید و core event log بسازید.
  6. split کاربرمحور train/eval را اجرا کنید.
  7. Rule-based / XGBoost را برای Ap/Tp و baseline اجرا کنید.
  8. WA و WA_recency را ارزیابی کنید.
  9. LSTM را با sequence، time_delta و persona embedding آموزش دهید.
  10. نتایج را سال‌به‌سال و سگمنت‌به‌سگمنت بررسی کنید.

۱۳. خطاهای رایج

چیزهایی که معمولاً خراب می‌شوند
خطا علت راه‌حل
اجرای script از ریشه پروژه relative pathها به‌هم می‌ریزند. هر script را از directory خودش اجرا کنید.
split نادرست leakage بین train و eval split را user-level نگه دارید.
فقط نگاه‌کردن به F1 over-prediction دیده نمی‌شود. rate_ratio و std را هم گزارش کنید.
حذف مدل rule-based تفسیر و teacher از بین می‌رود. baseline را نگه دارید، حتی اگر مدل آخر LSTM باشد.
استفاده از pipeline قدیمیِ non-split خروجی train/eval جداگانه تولید نمی‌شود. برای pipeline واقعی از core_eventlog_splited.py استفاده کنید.

۱۴. جمع‌بندی قابل ارائه

مرحله ۱ داده خام را به event log تبدیل می‌کنیم تا رفتار واقعی قابل اندازه‌گیری شود.
مرحله ۲ از داده، core actions را استخراج می‌کنیم تا فقط فعالیت‌های معنادار وارد مدل شوند.
مرحله ۳ پنجره‌ی زمانی Tp و آستانه‌ی Ap را از رفتار کاربران می‌سازیم، نه از حدس انسانی.
مرحله ۴ drift را سال‌به‌سال می‌سنجیم، چون رفتار کاربران در طول زمان تغییر می‌کند.
مرحله ۵ LSTM را برای یادگیری sequence و زمان آموزش می‌دهیم تا از baseline تفسیرپذیر عبور کنیم.
پیام اصلی: این pipeline فقط یک مدل نیست؛ یک روش قابل‌تکرار برای تبدیل رفتار خام کاربران به یک سیستم پیش‌بینی تفسیرپذیر و بعد sequence-aware است.
